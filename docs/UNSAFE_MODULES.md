# Declared unsafe system modules

Nivren's safe core does not expose arbitrary pointers, unchecked foreign calls, device access, or allocator ownership. A project that deliberately crosses that boundary must grant `Native` authority and name each system surface in its manifest:

```toml
[capabilities]
Native = "path:./native"

[unsafe]
memory = "allow"
layouts = "allow"
allocators = "allow"
atomics = "allow"
threads = "allow"
simd = "allow"
devices = "allow"
ffi = "allow"
```

The accepted module names are closed and fingerprinted into the project build. Unknown names, values other than `"allow"`, duplicate declarations, and unsafe modules without a `Native` grant are errors. This makes a systems boundary visible during review instead of treating all native access as one vague switch.

The modules correspond to these stable contracts:

| Module | Contract |
| --- | --- |
| `memory` | Owned bounded buffers and explicitly borrowed pointer/length views; foreign memory is represented by opaque handles or an integer address only inside unchecked FFI calls. |
| `layouts` | Fixed-width C11/C++17 layouts generated by `niv bindgen c`; no implicit Rust or VM object layout is stable. |
| `allocators` | Allocation and release remain a paired foreign ABI operation; `using` owns and deterministically releases the returned handle. |
| `atomics` | Sequentially consistent integer load/store/swap/add/compare-exchange through `std.atomics`; raw atomics belong behind the native boundary. |
| `threads` | Structured `start`/`wait` tasks are the safe surface; unmanaged foreign threads may interact only through callback and wake ABIs. |
| `simd` | Portable checked vector work must retain a scalar fallback; target-specific intrinsics are supplied by a declared native library. |
| `devices` | Devices are opaque owned handles opened through an allowlisted host kind and closed by `using`. |
| `ffi` | `std.native` finite signatures and bounded buffer ABI; symbol signature, pointer validity, and foreign behavior are the explicitly unchecked obligations. |

Unsafe declarations do not disable checked arithmetic, capability scopes, cancellation, resource budgets, or deterministic cleanup in the rest of the program. They acknowledge only the invariants that the compiler cannot verify at the named boundary. The main compiler and VM continue to forbid Rust `unsafe`; executable memory, dynamic loading, and C pointer handling remain isolated in the JIT, native-loader, and embedding crates.
